# playground CLI (Bashly)

The `playground` CLI is generated by [Bashly](https://bashly.dev) from
`scripts/cli/src/`. Editing the generated output is always wrong: the next
regeneration silently discards it.

## Never hand-edit these — all generated, all committed

| File | Produced by |
| --- | --- |
| `scripts/cli/playground` (~50k lines) | `bashly generate` |
| `scripts/cli/completions.bash` / `completions.zsh` | `send_completions bash\|zsh` (generated function, `completions: bash,zsh` in `settings.yml`) |
| `scripts/cli/playground.yaml` | `bashly render templates/shell-script-command-completion .` |
| `scripts/cli/playground.json` | `yq -o=json playground.yaml` |

They are tracked in git, so a CLI change is only complete once they are
regenerated **and** committed alongside the source edit.

The CLI reference pages (`docs/cli.md`, `docs/playground <command>.md`,
`docs/cli-pages.js`) are **not** tracked in this repository. `playground update-docs`
writes them into `docs/`, and the nightly CI `post-build` job ("Update DOCS")
generates and publishes them to the documentation site. `update-docs.yml` also
publishes them on every push to `master` touching the command tree
(`src/bashly.yml`, `src/commands/**.yml`, `src/flags/**`). A CLI change
needs nothing for those pages. If you ran `update-docs` locally, the pages it wrote
are ignored by `.gitignore`: never force-add them.

The **hand-written** pages (`docs/how-to-use.md`, `docs/toolkit-*.md`,
`docs/claude-code.md`…) are tracked here: when a
command or flag is new and worth mentioning, or renamed, update them in the same PR
(`grep -n "<old name>" docs/*.md`).

## The loop

1. **Declare** the command/flag in `scripts/cli/src/commands/<command>.yml`
   — one file per top-level command (see "Where the command tree lives" below).
   `src/bashly.yml` itself holds only the global settings and one
   `- import: src/commands/<command>.yml` line per command: do not add a
   command body there.
2. **Implement** it in `scripts/cli/src/commands/<command>/<subcommand>.sh` —
   one file per (sub)command, path mirroring the command tree exactly.
3. **Regenerate**: `playground bashly-reload`
   (requires Docker; pulls and runs `dannyben/bashly`). In a git worktree, run the
   worktree's own copy, `./scripts/cli/playground bashly-reload`: the `playground`
   on `PATH` derives `root_folder` from its own location and would regenerate the
   main checkout instead. Keep worktrees under `$HOME`, because Docker Desktop does not
   share `/private/tmp`, so the bashly container sees an empty folder there
   (`No such file or directory @ rb_sysopen - src/bashly.yml`).
4. **Verify**: `playground <cmd> --help`, one success path, one error path.
5. **Docs**: nothing to commit, CI publishes the CLI reference (see above).
6. Commit source **and** regenerated artifacts together, and check that the
   generated diff only contains your change (another uncommitted edit in the
   checkout gets inlined too).

Skipping step 3 is the classic failure: the flag exists in the YAML, the
partial reads `${args[--new-flag]}`, and the CLI ignores it entirely because
the parser was never rebuilt.

## Where the command tree lives

`src/bashly.yml` is ~230 lines: the global settings, flags and environment
variables, then one import per top-level command.

| File | Holds |
| --- | --- |
| `src/bashly.yml` | global settings + `- import: src/commands/<command>.yml` for each of the 88 top-level commands |
| `src/commands/<command>.yml` | the whole tree of that command — its subcommands, flags, args, examples |
| `src/flags/<flag>.yml` | **one** flag definition, shared by several commands |
| `src/commands/<command>/<sub>.sh` | the bash partial implementing a (sub)command |

Config (`.yml`) and code (`.sh`) sit side by side on purpose: everything about
`connector` is `src/commands/connector.yml` + `src/commands/connector/`.

### Sharing a flag between commands — not an anchor

**A YAML anchor cannot cross files.** `*verbose` in `src/commands/topic.yml`
referring to an `&verbose` defined in `src/commands/schema.yml` fails with
`Psych::AnchorNotDefined`. Anchors still work *inside* one file, and plenty of
commands use them for their own flags.

A flag used by more than one top-level command gets its own file instead:

```yaml
# src/flags/verbose.yml  — the flag mapping, at column 0
long: --verbose
short: -v
help: 🐞 Show command being ran.
```

```yaml
# used from any command file, at the right indentation
    flags:
    - import: src/flags/verbose.yml
```

Currently in `src/flags/`: `verbose`, `cluster`, `container`, `tag`,
`connect-tag`, `connector-tag`, `connector-zip`, `connector-jar`,
`force-refresh`, `level`, `compatibility-required`, plus the five
`analyze-*-flags` groups.

An `import` replaces **one list item**, so it only works for a single flag. For
a whole *list* of flags shared by two commands (the `analyze-*-flags` groups,
shared by `analyze` and `debug`), the file holds a YAML list and the command
file includes it with ERB, which bashly runs over the config before loading it:

```yaml
    flags:
<%= File.read('src/flags/analyze-logs-flags.yml').gsub(/^(?=.)/, '      ') %>
```

The ERB line **must start at column 0** and the string in `gsub` is the
indentation of the resulting flags (here 6 = the `flags:` indent + 2). Paths in
both `import:` and `File.read` are relative to `scripts/cli/`, not to the file
doing the importing.

## Where does the code go?

| What you're adding | Where |
| --- | --- |
| Logic for one command | `src/commands/<cmd>/<sub>.sh` |
| Helper used only by the CLI (fzf pickers, prompts, connector/topic lookups) | `src/lib/cli_function.sh` (~2400 lines) |
| Helper also used by example scripts | `src/lib/utils_function.sh` (~4200 lines — the real core library) |
| `playground.ini` read/write | `src/lib/ini.sh` |
| Argument validator | `src/lib/validations/validate_<name>.sh` |
| Command precondition | `filter_<name>()` in `src/lib/cli_function.sh` |
| Version / image defaults (`TAG`, `CP_*_IMAGE`, …) | `scripts/utils.sh`, on the line ending `# default tag` |

Everything under `src/lib/` is inlined into the generated script — no sourcing
needed, and any function there is callable from any command partial.

Do **not** put general-purpose helpers in `scripts/utils.sh`. That file is only
a thin entrypoint for example scripts: it sources `utils_function.sh` and sets
version defaults.

## Writing a command partial

Partials are function bodies, not standalone scripts. No shebang, no
`set -e`, no sourcing:

```bash
connector="${args[--connector]}"
verbose="${args[--verbose]}"

connector_type=$(playground state get run.connector_type)

if [[ ! -n "$connector" ]]
then
    connector=$(playground get-connector-list)
fi

log "⏸️ Pausing $connector_type connector $connector"
```

- Parsed flags/args arrive in the `args` associative array, keyed by the **long
  flag including dashes** (`${args[--connector]}`) or the arg name.
- Use `log` / `logwarn` / `logerror`, never bare `echo`.
- `$root_folder` (repo root) is set by `src/before.sh` and available everywhere.
- Call the CLI recursively — `playground state get …`, `playground connector
  status …`. That is the normal idiom, not a smell.
- `src/before.sh` runs before every command; it handles `--vvv` and
  `--output-level`.

## Conventions in the command files

Read `references/bashly-yml.md` for the full vocabulary as it is actually used
here (anchors, validators, filters, groups, completions). The essentials:

- **Reuse the shared flags, never re-declare one.** A flag used by several
  top-level commands is `- import: src/flags/<flag>.yml` (see above). Inside a
  single command file, a flag reused by several of its subcommands is a YAML
  anchor (`&connector` / `*connector`, `&subject` / `*subject`, …) — that still
  works, because anchor and alias are in the same file. If a flag that is
  currently an anchor becomes needed by a second top-level command, move it to
  `src/flags/` rather than copying it.
- **Help text is emoji-prefixed** (`🔗 Connector name`, `🗺️ Show a status`) and
  written for end users. Multi-line help uses `|-` with a blank line between
  paragraphs; `🎓 Tip:` marks hints.
- **`group:`** places a command under a heading in `playground --help`
  (Connector, Container, Debug, Kafka, Run, Schema, Topic, Tools, …).
- **`private: true`** hides a command from help and docs. Used for the
  `get-*-list` completion providers and for internal commands like
  `bashly-reload` and `state`. `PLAYGROUND_SHOW_PRIVATE=1 playground <cmd> --help`
  shows them (`private_reveal_key` in `scripts/cli/settings.yml`).
- **`environment_variables:`** documents the variables a partial reads, in an
  `Environment Variables:` section of `--help`. Mark the ones the CLI sets
  for its own nested calls `private: true`. Never add `required:` or
  `default:` to an existing variable: bashly enforces both.
- **`conflicts:`** is checked only against flags parsed *before* the flag
  that declares it, so declare a conflict on both flags (`--a` lists `--b`,
  and `--b` lists `--a`), otherwise one order on the command line passes.
- **Completions** call those private commands (bashly 2.x hash format):
  `completions: { dynamic: [playground get-connector-list] }`.
- **`filters:`** declare preconditions (`docker_running`,
  `connect_running`, `not_ccloud_environment`, `ccloud_environment`, …).
- **`validate:`** attaches a validator to an arg/flag (`validate_not_empty`,
  `validate_file_exists`, `validate_json`, `validate_minimal_cp_version`, …).

## Pitfalls

- **Docker must be running** for `bashly-reload`, `update-docs`, and the
  `docker_running` filter.
- Completions are answered at runtime by `playground __complete <words>`
  (bashly ≥ 2.0); `completions.bash`/`.zsh` are thin adapters forwarding to it.
  Inside a `dynamic` command the partial word is `$completion_current`
  (not `$cur`), and candidates not starting with it are filtered out.
- To test completions after a change, no re-sourcing is needed:
  `scripts/cli/playground __complete connector st`.
- A partial whose path doesn't match the command tree is silently never called.
- Private commands produce no documentation, so `update-docs` won't show them.
- Renaming or removing a flag is a breaking change for the ~300 example scripts
  that call `playground …`; grep the repo before doing it.
