# Contributing to kafka-docker-playground


The upstream repository is `vdesabou/kafka-docker-playground`. Track each feature or bug fix with a GitHub
issue and deliver it as a pull request linked to that issue.

- **Ask the user before creating an issue, and again before opening a PR** (or pushing new commits to an
  existing PR branch). Agreeing to one does not cover the next.
- **Avoid duplicates and redundant work.** Search first with
  `gh issue list --state all --search "<keywords>"`, and check `git log origin/master`, since the change may
  already be there.
- **Issue:**
  - Title: emoji prefix + short sentence, matching existing issues: `🐛 …` bug, `🧠 …` CLI improvement,
    `🧹 …` cleanup, `👾 Add … Fully Managed Connector example`, `⭐ …` big feature. Add a second emoji
    for the topic of the change after the type one (2 emojis max), e.g. `🐛⏱️ connector wait times out…`,
    `🐛🔐 sasl-ssl …`, `🧠📊 benchmark …`, `🧠📚 docs …`, `🧠🔍 find-example …`.
  - Labels: `enhancement ✨` for features and `bug 🐛` for fixes, written exactly like that (emoji
    included). Add `cfk` if the change is specific to the cfk environment. Never use `new 🆕`,
    `CI failing 🔥` or `CI ignore ⏭️`: they are reserved for CI-generated issues.
  - Milestone: the milestone of the current month, `MM-YYYY` (for example `10-2026`): `gh issue create --milestone "$(date +%m-%Y)"`. If it doesn't exist yet, create it first: `gh api repos/vdesabou/kafka-docker-playground/milestones -f title="$(date +%m-%Y)"`.
  - Body: a short, standalone description of the problem and the change.
- **Commit:** same title as the issue, ending with ` #<issue number>`. Commit only the files of the change:
  - never the private `reproduction-models` submodule
  - never `playground.ini`, `playground-run-history`, `.ccloud/`, `secrets.properties` or key files
  - never generated files: hand edits to `scripts/cli/playground`, or the untracked `docs/cli.md`, `docs/content.md`, `docs/playground *.md`… written by a local `update-docs` / `update-readme`.
    Regenerate them instead (see "Docs generation" below).
- **Pull request:**
  - Branch off `master` with a descriptive name (for example `fix-<issue>-<slug>`). Push to your fork if
    you don't have write access to the upstream repository.
  - Open it with `gh pr create --base master`, using the issue title. The body must contain
    `Fixes #<issue number>`.
  - Use the same labels as the issue, and no milestone (only the issue has one).
- **CI:** a new example only runs in CI once its directory is added to a 🚀 line of the `test_list` matrix
  in `.github/workflows/ci.yml` (see "Testing" in CLAUDE.md).

## Docs generation

The website is published from [`vdesabou/kafka-docker-playground-docs`](https://github.com/vdesabou/kafka-docker-playground-docs) (GitHub Pages on `main:/docs`, [Docsify](https://docsify.js.org)), but its **sources live in `docs/` of this repository**. `scripts/publish-docs.sh` copies `docs/` there. It runs from `update-docs.yml` (on every push to `master` touching `docs/**` or the CLI command tree `scripts/cli/src/{bashly.yml,commands/**.yml,flags/**}`), from the nightly `ci.yml` and from `update-changelogs.yml`. To publish everything now (content.md included, from the last CI results), use **Run workflow** on Update Docs: `gh workflow run update-docs.yml --repo vdesabou/kafka-docker-playground`.

| In `docs/` here | What it is |
| --- | --- |
| `how-to-use.md`, `how-it-works.md`, `reusables.md` and the `toolkit-*.md` pages it links to, `sessions.md`, `reports.md`, `claude-code.md`, `academy.md`, `legacy-java-producer.md`, `sidebar.md`, `_coverpage.md`, `_404.md`, `index.html`, `llms.txt`, `assets/` | hand-written pages: edit them here, in the same PR as the change they document |
| `content-template.md`, `badges-template.md`, `introduction-header.md`, `introduction-footer.md` | templates: `playground update-readme --tags "<tag>"` turns them into `content.md`, `badges.md`, `introduction.md` by scanning the example directories and CI results. The nightly CI runs it (and manages the 🔥 issues); `update-docs.yml` runs it with `--skip-gh-issues` when one of these templates changed since its last successful run (a run cancelled by a later merge is caught up by the next one), and on Run workflow |
| *(not tracked)* `cli.md`, `index.md`, `playground <command>.md`, `cli-pages.js` | generated by `playground update-docs` from the CLI command tree (`scripts/cli/src/bashly.yml` + `src/commands/*.yml`) and `scripts/cli/docs-template/cli-template.md` |
| *(not tracked)* `changelog.md` | generated by `update-changelogs.yml` from closed milestones |

- Never commit the generated files here, and never edit hand-written pages in the docs repository: the next publication overwrites them there, and a page deleted or renamed here is deleted there too.
- Media stay in the docs repository: `videos/`, `images/` and the reports gallery `reports/`, together with the VHS `tapes/` and `scripts/generate-*.sh` that record them. The reports gallery (`docs/reports/`, `docs/images/reports/`) is regenerated and pushed there by `update-reports-gallery.yml` when a merged change touches an analyzer, a report, a sample or the commands that write them (a pull request gets a dry run, the reports as an artifact): no hand-run `generate-reports-gallery.sh` nor docs PR for it. A new sample in the gallery is still a line in that script (docs repository) plus its card in `docs/reports.md` here. Pages here reference them with relative paths (`images/x.png`, `videos/x.mp4`), so they only resolve on the website, not in a local `npx docsify-cli serve docs`.
- When a command or flag is renamed, grep `docs/*.md` for the old name and fix the hand-written pages in the same PR.
